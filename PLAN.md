# snapping-turtle — Implementation Plan (v0.15)

A self-hosted screenshot capture and sharing system: browser extensions (Chrome + Firefox) capture the current tab — and, since M9, a native Linux client captures a screen, window or region — upload it to a central server, and open an editor page at an unguessable URL. The owner can annotate with red/white arrows, rectangles, and text; anyone with the link can view the page, copy a flat rendered image link, and follow a link back to the original site. The server is designed defensively from day one: capability URLs with high entropy, aggressive anti-enumeration controls, attribution of every upload, admin audit logging, automated TLS, and a 30-day default retention policy.

This document is the record of a completed v1 (M0–M8, §16). Section 2 records the confirmed decisions; nothing in it is still open — the three UX questions it once carried are deferred to §17 with their reasoning. v0.4 records the M1 implementation notes (a `sessions` table, the exact auth/token routes, throttle keying, and what `image.png` serves before M4); v0.5 records the M2 extension notes (the `notifications` permission, Firefox 128 minimum, runtime host grants, the ping route, and why capture itself is manually tested); v0.6 records the M3 editor notes at the end of §9 (beacon CSRF-in-body, validation constants, owner-only PATCH until M5, fit-width scaling, and the tall-canvas spike results); v0.7 records the M4 renderer notes at the end of §10 (the vendored font + fontconfig contract, the forced pango backend, ETag/304 semantics, and the parity tolerances); v0.8 records the M5 guard notes at the end of §12 and the M5 admin/lifecycle notes at the end of §11 (the `st_app` role split that makes the audit log append-only at the grant level, the one-time-link mechanics, and the admin unban); v0.9 records the M6 capture notes at the end of §15 (the measured Firefox `captureTab` scale semantics, the two-phase region protocol, the stitch geometry rules, and the known limitations); v0.10 records the M7 operations notes at the end of §12 and §13 (the purge job's ordering and idempotency rules, the backup sidecar and its verified restore, the `sec.*` event taxonomy, the k6 guard results, and the supply-chain gates in CI); ## 1. Goals and non-goals

**In scope (v1):** visible-viewport, selected-region, and full-page capture from Chrome and Firefox; upload with attribution; secret shareable page per capture; owner-only annotation (rect / arrow / text, red with white outline, draggable and resizable); flat PNG rendering with a copyable direct link; link back to the capture's source page; accounts with an admin-controlled registration toggle; per-image retention (30-day default, owner-extendable, admin-indefinite); rate limiting + circuit breaker against URL enumeration; Docker deployment with automated Let's Encrypt TLS; single-variable domain migration.

**Explicit non-goals (v1):** video/GIF capture, teams/shared ownership, comments, mobile apps, multi-node scaling, S3/object storage, federation. These are listed in §17 as future options so nothing in v1 paints us into a corner.

Everything below is settled (last updated 2026-08-30); the plan is written against these.

## 3. System architecture

Four deployable pieces plus a reverse proxy — two capture clients that are peers of each other (the browser extension and, since M9, the native Linux client) speak the same upload API:

```
┌────────────────────┐   HTTPS    ┌─────────────────────────────────────────┐
│ Browser extension  │──upload──▶ │  Caddy (TLS via ACME DNS-01, limits)    │
│ (Chrome / Firefox) │            │        │ reverse_proxy                   │
└────────────────────┘            │        ▼                                 │
┌────────────────────┐            │  app (Fastify, Node)                     │
│ Linux client (Rust)│──upload──▶ │                                          │
│ tray · portal/KWin │            │                                          │
┌────────────────────┐            │   ├── API (upload, annotations, auth,    │
│ Any viewer with a  │──view────▶ │   │    admin, retention)                 │
│ secret link        │            │   ├── Pages (viewer/editor, login,       │
└────────────────────┘            │   │    account, admin) — static Vite     │
                                  │   │    bundles + JSON API                │
                                  │   ├── Renderer (sharp: flat PNG)         │
                                  │   ├── Guard (bans, rate limits, breaker) │
                                  │   └── Jobs (retention purge, render GC)  │
                                  │        ▼                                 │
                                  │  PostgreSQL          image volume        │
                                  └─────────────────────────────────────────┘
```

**Capture flow:** the user picks a mode — visible, region, or full page — from the toolbar popup or a per-mode keyboard shortcut → the extension produces a PNG (per-mode mechanics in §15) → `POST /api/v1/captures` with bearer token, image blob, source URL, and page title → server validates, re-encodes, stores, creates DB row → returns `{ pageUrl }` → extension opens a new tab at `pageUrl`. The Linux client (§15a) runs the same flow from a tray menu, desktop actions or portal global shortcuts — full screen / region / window — with a generated title and no source URL, and opens `pageUrl` through the OpenURI portal. The editor page is served by the server, not the extension, so the owner can return and edit from any signed-in browser.

**View flow:** `GET /s/{viewId}` renders the page. Non-owners get the current flat PNG plus the source link and copy buttons. The signed-in owner gets the interactive editor over the original image.

**Edit flow:** the editor mutates a local annotation document and autosaves via `PUT /api/v1/captures/{viewId}/annotations` (debounced ~800 ms, plus `sendBeacon` on unload). Each save bumps a revision counter, which invalidates the cached flat render.

## 4. Technology choices

**Server:** Node 22 + Fastify. Fastify gives schema-validated routes (TypeBox), sensible defaults, and mature plugins for cookies, CSRF, and static serving. **Database:** PostgreSQL 16 via Drizzle ORM (thin, SQL-transparent, easy to audit). SQLite would honestly survive this scale, but Postgres removes a class of write-concurrency questions around autosave and makes backup tooling boring. **Image processing:** `sharp` for ingest re-encoding and flat rendering. **Editor:** Fabric.js v6 — it ships selection handles, drag/scale transforms, and in-place text editing (`IText`), which covers "draggable, resizable, stretchable" with very little custom code. **Frontend build:** Vite, vanilla TypeScript (no framework needed for four pages). **Proxy/TLS:** Caddy 2 — automatic Let's Encrypt issuance and renewal with zero cron jobs and HSTS in ~10 lines of config (since v0.12 through the DNS-01 challenge on a single published port, §14; there is no HTTP listener to redirect from). **Passwords:** argon2id. **Logging:** pino structured JSON. **Linux client (M9):** Rust — the one exception to TypeScript end-to-end, recorded in CLAUDE.md: ashpd is the maintained first-class portal binding, the result is one dependency-light binary, and the client shares nothing with the renderer where the shared-types rule matters (§15a).

The extension, editor, and server share one package for the annotation schema and API types, which keeps the client renderer and the server-side flat renderer geometrically in lockstep (§9–10). The Linux client mirrors the handful of constants it needs and proves them against `shared/src/constants.ts` in its own tests.

## 5. Data model

| Table | Key columns | Notes |
|---|---|---|
| `users` | id, username, password_hash, role (`user`/`admin`), disabled_at, created_at | First admin bootstrapped by a seed command reading env vars |
| `api_tokens` | id, user_id, name, token_hash (sha256), created_at, last_used_at, revoked_at | Plaintext shown once at creation; scoped to upload only |
| `captures` | id, view_id (unique, secret), owner_id, source_url (nullable since M9), page_title, width, height, bytes, sha256, upload_ip, upload_token_id, created_at, retention_until (nullable = indefinite), deleted_at, annotations (jsonb), annotations_rev, flat_rev | `view_id` is the only public identifier; sha256 supports dedup checks and abuse tracking |
| `sessions` | token_hash (sha256, PK), user_id, created_at, expires_at, last_seen_at | Server-side browser sessions (added in M1): revocable on disable/reset; the cookie carries the random token, only its hash is stored |
| `settings` | key, value | e.g. `registration_enabled` — runtime-togglable by admin |
| `audit_log` | id, at, actor_user_id, action, target_type, target_id, detail (jsonb), ip | Append-only; the app role has no UPDATE/DELETE grant on it |
| `ip_bans` | ip_prefix, strikes, banned_until, reason, updated_at | Persisted so restarts don't amnesty an attacker; `strikes` outlives `banned_until` so escalation carries across bans |
| `account_links` | id, user_id, purpose (`setup`/`reset`), token_hash (sha256), expires_at, consumed_at, created_by, created_at | Admin-issued one-time set-password links (§11): 24 h expiry, consumed on first use, raw token shown to the admin exactly once (M5) |

Deleting a capture removes the image files immediately but leaves a tombstone row (owner, source_url, sha256, timestamps) for 90 days to support trust-and-safety follow-up; the purge job hard-deletes tombstones after that.

*M9 (2026-09-03):* `source_url` is nullable. The always-present source link (§7) was browser-capture-specific by construction — a tab always has a URL — and the native Linux client (§15a) captures a screen, a window or a region that has none. Browser uploads keep sending it; a NULL means "no source page", never "unknown".

## 6. Identifiers and link secrecy

`view_id` is 20 bytes from a CSPRNG, base64url-encoded → 27 characters ≈ 160 bits of entropy. At an absurdly generous 10,000 guesses/second, expected time to find one valid ID among even a million stored images is ~10^30 years — enumeration is only feasible if we leak information, so the design focuses on not leaking:

- **Uniform not-found behavior.** Never-existed, expired, deleted, and taken-down IDs all return the identical generic 404 page, same headers, with small random latency jitter. No oracle distinguishes "expired" from "never existed."
- **No discovery surface.** No listing endpoints, no sitemap, `robots.txt` disallows `/s/`, and every secret route sends `X-Robots-Tag: noindex, nofollow`.
- **No referrer leakage.** Secret pages set `Referrer-Policy: no-referrer`, and the "open original page" link carries `rel="noopener noreferrer"` — otherwise clicking through to the source site would hand that site the secret URL.
- **No cache leakage.** Secret pages are `Cache-Control: private, no-store`; flat images are cacheable but only under their own secret path.
- **Link previews are a sharer's choice, not a discovery surface (E3, 2026-09-02).** Live capture pages carry Open Graph tags (`og:title` = the capture's title, `og:url`, `og:image` = the flat PNG with its type and pixel size, a fixed `og:description`, `twitter:card=summary_large_image`), all absolute from `PUBLIC_ORIGIN`. §17 originally deferred this on the grounds that a preview bot fetching the capability URL would need guard whitelisting and would populate a cache the owner cannot expire. On reflection the first is false and the second is already the case: a preview bot fetches a URL only when someone who already holds it posts it into a chat — that is the sharer's decision and exactly what the capability model allows (whoever has the link has the screenshot, and any chat client would have fetched and cached the image anyway) — and the bot is ordinary anonymous traffic to a valid link, well inside the general cap. So there is **no guard special-casing for preview bots**: user agents are spoofable, and allowlisting `Discordbot`/`Slackbot` through the invalid-lookup budget or bans would be a rule-9 bypass in a costume; a bot that trips a ban recovers when the ban expires. The uniform 404 is untouched — no tags on any not-found state, byte-identical across never-existed, deleted, expired and malformed — and the header posture above stays on with the tags (`noindex` governs indexing, not unfurling; preview crawlers fetch fresh and need no caching). A per-capture opt-out is noted in §17, not built.

Routes: `GET /s/{viewId}` (page) and `GET /s/{viewId}/image.png` (flat render). Both derive from the one secret; a future enhancement is a separately rotatable image-only token if owners want to share the picture without the page. The image URL is part of the link contract from M1: until the renderer lands in M4 it serves the re-encoded original, and M4 changes only what the same URL returns. The uniform-404 rule applies to *every* path under `/s/` — malformed ids and unknown sub-paths included — with a random delay (`RATE_NOT_FOUND_JITTER_*`, default 30–150 ms).

## 7. The capture page

Every capture page shows, for all visitors: the annotated image (flat render for non-owners, live canvas for the owner), a prominent **"Open original page"** link to `source_url` when the capture has one (every browser capture does; a desktop capture from the Linux client has none and the link is omitted — M9), and two copy buttons — **copy page link** and **copy image link** (the flat PNG URL). For the owner it additionally shows the editor toolbar, a retention selector (30/90/180/365 days), and delete. Admins viewing any capture also see the **"Keep indefinitely"** checkbox (writes `retention_until = NULL`, audit-logged).

Captures of internal tools embed internal URLs in `source_url`, visible to anyone with the link. The spec requires the link be present, so v1 always shows it; an owner-side "hide source link" toggle is deferred backlog (§17). *M9:* the requirement was always about browser captures — the link is "the feature's second half" only when there is a page to go back to. A source-less capture renders the same page minus the anchor (same headers, same preview tags with the title alone as `og:title`, same copy buttons); it is not a third response shape, and the uniform 404 is untouched.

Since E3 every live capture page — the view-only render and the owner's editor variant alike — also carries link-preview tags in `<head>` (Open Graph plus the Twitter card type), so a pasted link unfurls with its annotated image in Discord-style previews; the title is escaped as attribute data like everything else on the page (`server/src/html.ts`, `previewTags`). The rationale and the boundaries are recorded in §6.

| Route | Auth | Purpose |
|---|---|---|

| `GET /` | none | Home page (E2): server-rendered — name, one line, install cards (Firefox via `/ext/firefox-latest` when published, else "not yet published"; Chrome via `CHROME_EXTENSION_URL` when set, else "coming soon"), sign-in link |
| `GET /s/:viewId` | none | Viewer/editor page (with link-preview tags since E3) |
| `GET /s/:viewId/image.png` | none | Flat render (cached) |
| `GET/PUT /api/v1/captures/:viewId/annotations` | session (owner) | Load/save annotation doc; PUT requires matching `rev` |
| `PATCH /api/v1/captures/:viewId` | session (owner/admin) | Retention changes, delete |
| `POST /api/v1/auth/signup` | none (if enabled) | Gated by `registration_enabled` |
| `POST /api/v1/auth/login`, `/logout`; `GET /api/v1/auth/me` | — / session | Session cookie `st_session`: HttpOnly, Secure (when the origin is https), SameSite=Lax, signed; `/me` returns username, role and the CSRF token |
| `GET /reset/:token` → `POST /api/v1/auth/set-password` | valid single-use token | Set-password page for admin-issued setup/reset links (§11) |
| `GET/POST /api/v1/tokens`, `DELETE /api/v1/tokens/:id` | session | Manage extension API tokens (revoke = set `revoked_at`; rows are kept for attribution) |
| `GET /api/v1/ping` | Bearer token | 204 with no body; the extension's "Test connection" target (M2). Bumps the token's `last_used_at`; invalid/revoked tokens and disabled users get the same 401 as upload |
| `GET/POST /api/v1/admin/*` | session (admin) | Settings toggle, user create/disable, set-password link issuance, capture search by user, audit log view — every mutation audit-logged |
| `GET /ext/updates.json`, `GET /ext/snapping-turtle-firefox-<v>.xpi` | none | Self-distributed Firefox build (§15, M8) |
| `GET /ext/firefox-latest` | none | 302 to the newest `.xpi` named in `updates.json`, resolved per request (E2); plain 404 until one is published |
| `GET /healthz` | internal only | Compose healthcheck |

All state-changing browser routes require a CSRF token (double-submit) on top of SameSite: the token is an HMAC of the session, delivered in a readable `st_csrf` cookie and by `/me`, and must be echoed in `x-csrf-token`. One deliberate variant (M3): the editor's unload save uses `sendBeacon`, which cannot set headers, so `POST /api/v1/captures/:viewId/annotations` accepts a `text/plain` body of `{ csrfToken, document }` and verifies the same token from the body — semantics otherwise identical to the PUT. Token-authenticated upload is exempt (no cookie ambient authority) and, conversely, never accepts a cookie as authentication. Upload is `multipart/form-data` with fields `image`, `sourceUrl`, `title` (names in `shared/` `CAPTURE_UPLOAD_FIELDS`). Since M9 `sourceUrl` is optional — absent or blank stores NULL; when present it is validated exactly as before (http(s), length-capped, normalised).

## 9. Annotation editor

Fabric.js canvas sized to the image's native pixels, scaled to fit the viewport. Toolbar: select / rectangle / arrow / text / delete / undo-redo (in-memory undo stack).

- **Rectangle:** click-drag to draw at any size; afterwards fully draggable and stretchable via corner/edge handles.
- **Arrow:** click-drag from tail to head; rendered as a line + head with endpoint handles so either end can be repositioned (a custom two-handle control rather than Fabric's default bounding-box scale, which distorts arrowheads).
- **Text:** click to place an `IText` box; double-click to edit; draggable and resizable (font size scales).

**Red-with-white-outline styling** is done by double-stroking: each shape is drawn once in white at `strokeWidth + 4` and once in red on top (Fabric group), and text uses white stroke under red fill with `paintFirst: 'stroke'`. The same trick is reproduced verbatim in the server renderer so both outputs match.

**Persistence format** is our own JSON (not Fabric's serialization, which would couple the server to a library version):

```json
{ "version": 1, "rev": 12, "shapes": [
  { "id": "a1", "type": "rect",  "x": 120, "y": 80, "w": 300, "h": 140 },
  { "id": "a2", "type": "arrow", "x1": 40, "y1": 400, "x2": 210, "y2": 260 },
  { "id": "a3", "type": "text",  "x": 500, "y": 60, "text": "look here", "fontSize": 28 }
] }
```

Server-side validation caps the document: ≤ 500 shapes, text ≤ 2,000 chars/shape, coordinates within image bounds ± margin, control characters stripped. `PUT` with a stale `rev` returns 409 and the editor reloads (last-writer-wins across the owner's own tabs is acceptable for v1). Text is treated strictly as data — rendered via `textContent` in the DOM and escaped into SVG on the server — never interpolated as markup.

Full-page captures make the canvas tall. A single Fabric canvas up to the ~32,000 px cap is workable on desktop, but M3 includes a performance spike on the tallest fixtures; if interaction lags, the fallback is windowed rendering — only the visible slice of the image is on canvas, while annotations live in image coordinates throughout, so nothing else changes.

*M3 implementation notes (v0.6):* the editor ships on Fabric.js **6.9.1** (v7 exists; v6 is what this plan vetted, and it runs clean under the strict CSP — no `unsafe-eval`). Validation constants: coordinates may overhang the image by `ANNOTATION_BOUNDS_MARGIN_PX` (100 px) per side, and the PUT body is capped at `MAX_ANNOTATION_DOC_BYTES` (8 MB — 500 two-thousand-character text shapes are legitimate). The document is validated in the handler with TypeBox `Value.Check` rather than route-level Ajv, because Ajv's `removeAdditional` mutates union branches while evaluating them and corrupts the shape union; no unvalidated field reaches business logic either way. The validator is an implementation detail and the wire contract is not: `shared/test/fixtures/annotation-corpus.ts` records 105 documents with their accept/reject outcome, reason category and persisted form (snapshotted under TypeBox 0.34 before the move to TypeBox 1.x), and two rules the libraries disagreed on are now stated in `shared/` rather than inherited — `maxTextLength` counts UTF-16 code units (what the editor's `slice` produces; 1.x would count code points) and a sparse `shapes` array is invalid (1.x skips holes). `PATCH /api/v1/captures/:viewId` is **owner-only in M3** — the admin half of the table row (indefinite retention, delete-any) arrives with the M5 panel, and annotations stay owner-only forever (admins get 403). The owner's retention selector re-anchors expiry at `created_at + days`, so the choice is idempotent and displayable. The canvas scales fit-to-width (capped at 1:1) and tall captures scroll vertically — fit-to-viewport would render a 32,000 px capture unreadably small. Rotation controls are disabled on every shape; the schema carries no rotation, and the editor must not outrun what M4's renderer can reproduce. The double-stroke geometry (red 4 px over white 8 px, arrowhead 22×18, text stroke 4 px, Inter) lives in `shared/` `ANNOTATION_STYLE` for both renderers. The spike results (see `docs/perf-tall-canvas.md`) came in comfortably interactive at the 150 MP ingest ceiling — note that ceiling makes the tallest possible fixture 4,680 × 32,000, not 10,000 × 32,000 — so windowed rendering stays a designed fallback, unbuilt.

*E1 — adaptive annotation sizing (v0.13, 2026-09-02):* the fixed `ANNOTATION_STYLE` sizes are gone; every drawing size is a pure function of the capture's **width**, `annotationSizes(width)` in `shared/src/annotations.ts`. Viewing is fit-to-width, so width-proportional sizing means a constant *apparent* size; height is deliberately ignored so a tall full-page capture does not get giant strokes. Each size is `clamp(k · width, min, max)` with `k = base / 1280`, `min = 0.75 · base`, `max = 6 · base` (`ANNOTATION_SIZE_CURVE`; the `base` values are the pre-E1 constants, so a 1,280 px capture renders exactly as before). The floor engages below 960 px (small region crops display at natural size and keep legible strokes); the ceiling above 7,680 px (nothing grows past 6×, so the widest captures stop short of cartoonish). Sizes round to two decimals so both renderers receive identical numbers.

| width (px) | scale | red stroke | white rim | outer band | arrowhead L×W | text stroke | default text |
|---|---|---|---|---|---|---|---|
| 300 (region crop, floor) | 0.75 | 3 | 1.5 | 6 | 16.5 × 13.5 | 3 | 21 |
| 960 (floor boundary) | 0.75 | 3 | 1.5 | 6 | 16.5 × 13.5 | 3 | 21 |
| 1,280 (reference) | 1 | 4 | 2 | 8 | 22 × 18 | 4 | 28 |
| 1,920 | 1.5 | 6 | 3 | 12 | 33 × 27 | 6 | 42 |
| 2,560 (1,280 CSS px at 2×) | 2 | 8 | 4 | 16 | 44 × 36 | 8 | 56 |
| 3,200 | 2.5 | 10 | 5 | 20 | 55 × 45 | 10 | 70 |
| 5,120 | 4 | 16 | 8 | 32 | 88 × 72 | 16 | 112 |
| 7,680 (ceiling boundary) | 6 | 24 | 12 | 48 | 132 × 108 | 24 | 168 |
| 10,000 (ingest width cap) | 6 | 24 | 12 | 48 | 132 × 108 | 24 | 168 |

`shared/test/annotation-sizes.test.ts` pins this table; `shared/test/style-literals.test.ts` fails if a literal stroke or font size reappears in either renderer (`web/src/editor/**`, `server/src/images/**`). The model is fixed, the numbers are not: retune `ANNOTATION_SIZE_CURVE`, update this table, bump `RENDER_VERSION` (§10) and regenerate the goldens in one change.

**The wire format did not change.** The schema stays version 1 and stored `fontSize` stays absolute pixels; only the *default* for newly placed text comes from the width, and a user resize stores absolute pixels exactly as before. The TypeBox corpus (`shared/test/fixtures/annotation-corpus.ts`) passed unmodified. Storing relative units or bumping the schema version would be a different, larger change and was explicitly not started. The arrow's endpoint handles are screen-space editor chrome and do not follow the curve.

**Existing content re-renders with the new sizes — decided, not accidental.** Every pre-E1 annotation (including already-shared links) is drawn with the adaptive sizes on its next view, because the flat cache is versioned (§10 `RENDER_VERSION`) and the editor has no other sizes to use. Captures at or near 1,280 px are pixel-identical; narrower ones get slightly thinner strokes (floor 0.75×) and wider ones thicker. Accepted because this deployment is days old with little shared content, and because the alternative — persisting a per-capture "renderer generation" so old captures keep old sizes forever — would fork the renderers into two styles for no reader's benefit. A future compatibility question should start here: there is one style, and it is whatever `annotationSizes()` says today.

Deferred from E1: per-shape user-adjustable stroke width (§17).

## 10. Flat image rendering

`GET /s/:viewId/image.png` serves a cached composite when `flat_rev == annotations_rev`; otherwise it renders: build an SVG overlay from the annotation JSON (white-under-red double strokes; text via `<text>` with `paint-order: stroke`), then `sharp(original).composite([overlay]).png()` and cache to disk. The Docker image bundles `fontconfig` plus one pinned font (e.g. Inter) so librsvg text rendering is deterministic across rebuilds. A golden-file test renders a fixture annotation set on both the Fabric canvas (via Playwright) and the server path and diffs them within a pixel tolerance, guarding parity as either side is upgraded. Renders happen in a small worker queue (concurrency ~2) so a burst of viewers can't turn image rendering into a CPU-exhaustion vector.

*M4 implementation notes (v0.7):*

- **One font file, both renderers.** The pinned font is vendored in the repo — `shared/fonts/Inter-Regular.ttf` (Inter 4.1 static Regular, SIL OFL) — not installed from a distro package, so the glyphs cannot drift between environments. The editor loads it via `@font-face` (and awaits `document.fonts` before mounting Fabric); the server registers it through `server/fontconfig/fonts.conf`, pointed at by `FONTCONFIG_PATH` (defaulted in code by `pinRendererFonts()`, and as ENV in the Docker image, whose runtime also installs the `fontconfig` package). One finding worth keeping: sharp's **macOS** binaries build pango with the CoreText backend, which ignores fontconfig entirely and resolves system fonts — so the renderer also sets `PANGOCAIRO_BACKEND=fontconfig` (a no-op on Linux) or local renders would use whatever the Mac has installed. The container's filesystem is read-only, so `XDG_CACHE_HOME=/tmp` sends the fontconfig cache to the tmpfs.
- **Geometry contract.** The SVG renderer mirrors verified Fabric 6.9.1 behavior: rect and text bounding boxes include `strokeWidth` (paths and glyph boxes sit at `+strokeWidth/2`), arrows draw at absolute endpoint coordinates, and text baselines derive from the Fabric metrics pinned in `shared/` `ANNOTATION_TEXT_LAYOUT` (`lineHeight` 1.16, `fontSizeMult` 1.13, `fontSizeFraction` 0.222), which the editor re-asserts on every `IText` so a Fabric upgrade cannot silently move glyphs. librsvg's `paint-order: stroke` support was verified before building on it.
- **HTTP contract.** The flat URL is stable while its content tracks edits, so responses carry `ETag: "r{annotations_rev}"` (since E1 `"r{annotations_rev}-v{RENDER_VERSION}"`, see the E1 notes below) with `Cache-Control: private, no-cache`; `If-None-Match` on the current revision returns 304 before any file or render work. Captures with zero shapes serve the re-encoded original untouched (no composite, no cache file). The cache is one overwritten file per capture (`{id}.flat.png`), written before `flat_rev` is bumped so the marker never claims a missing render; deleting a capture removes it with the original, and no separate GC exists or is needed.
- **Stampede control.** Renders go through a concurrency-2 gate with per-capture single-flight; the render job re-reads the row so coalesced viewers get the freshest revision, and a save racing a render leaves `flat_rev` stale for the next request to repair. Render logs carry internal capture ids only, never `view_id`s.
- **Parity tolerances (measured, then capped with headroom).** pixelmatch per-pixel threshold 0.1; shape-only fixtures measured 0.000% differing pixels (geometry is exact) and are capped at 1% — enough to fail a deliberate 3 px displacement (verified); text fixtures measured 1.2–3.8% (Skia vs librsvg antialiasing of identical glyphs) and are capped at 5%. Server-only goldens live in `server/test/golden/` (0.5%/2% caps; regenerate deliberately with `UPDATE_GOLDENS=1`). The structural fallback for text (glyph bounding boxes + color sampling) was not needed; it remains the designed fallback if a platform pushes text diffs past the cap.

*E1 implementation notes (v0.13, 2026-09-02):*

- **Sizes come from the capture width** (§9): `buildOverlaySvg()` calls `annotationSizes(width)` once per render, exactly as the editor does once per capture, so the flat render and the canvas agree at every width. Stored `fontSize` is drawn as-is; only the white underlay stroke scales.
- **Renderer version in the cache and the validator.** `captures.flat_render_version` (migration 0003, default 0 = "rendered before versioning") records the shared `RENDER_VERSION` that drew the cached file; the route serves the cache only while `flat_rev == annotations_rev` **and** `flat_render_version == RENDER_VERSION`, and `ensure()` re-stamps both after a render. So a renderer change re-renders every capture lazily on its next view through the same concurrency-2 gate — no mass job. The ETag is now `"r{annotations_rev}-v{RENDER_VERSION}"`: a client revalidating a pre-E1 render must miss, or it would 304 forever. Integration test: a row stamped with an older version and a planted sentinel cache file re-renders exactly once despite matching revs, and the old tag does not 304.
- **Parity matrix.** The fixtures now include one rect, arrow and text fixture at each of 300 / 1,280 / 3,200 / 10,000 px (`PARITY_WIDTHS`), and the rect fixtures carry a `strokeBand` probe: both renderers must paint exactly `outerStrokeWidth` consecutive pixels through the top edge — 6 px on the floor, 8 at the reference, 20 at 3,200, 48 on the ceiling — measured on the pixels, so the clamps are proven in both renderers, not just in the function. The six 480 px fixtures from M4 stay (now on the floor, scale 0.75). Goldens regenerated; 18 files, ~1 MB.
- **Parity metrics re-based, and a harness bug found.** The M4 harness guarded its font load with `document.fonts.check('16px Inter')`, which returns *true* when no face named Inter is registered — so it never loaded Inter and rendered every fixture in Chromium's fallback font, ~11% narrower than the server's Inter. The M4 tolerance (5% of *image* pixels) passed anyway because a whole-image ratio dilutes with area; the "1.2–3.8% text differences" above measured that mismatch, not antialiasing. E1 loads the font unconditionally, and the spec now checks (1) the painted extent (ink bounding box) agrees within **1 px**, and (2) pixelmatch differences over the *painted* pixels stay under **30%**. Calibrated on all 18 fixtures: box delta 0–1 px, ink ratio 0–15.9% (shapes; the floor fixtures' 1.5 px rims are all edge pixels) and 0.01–15.1% (text). Deliberate faults: a 2 px rect shift and a 3 px text baseline shift each move the box by 2–4 px on every fixture (caught), and push ratios to 16–44% below 3,200 px. The 3 px shape displacement M4 verified is still caught, now at every width. Server-only goldens keep their whole-image caps (0.5% / 2%) — they compare a renderer with itself across platforms, where dilution is not the concern.
- **Existing content**: see the end of §9 — pre-E1 flats re-render with the adaptive sizes by design.

## 11. Accounts, ownership, admin

Username + password (argon2id), session cookies, per-account login throttling with exponential backoff on failures (in-process, keyed by the *attempted* username whether or not it exists, so the throttle reveals nothing about which accounts are real; `LOGIN_THROTTLE_*` knobs, defaults in `shared/`). Signup page exists at `/signup` but returns "registration is closed" unless the admin has enabled it — the toggle lives in `settings`, changeable at runtime from the admin panel, and both states of the toggle are audit-logged. Users generate extension tokens on an account page; tokens are stored hashed, revocable, and record last-use. Every capture stores owner, token used, and upload IP, satisfying full attribution.

Because registration will usually stay disabled in a friends-only deployment, the admin panel covers the whole account lifecycle with one mechanism: **single-use links**. *Create user* takes a username and returns a one-time set-password URL the admin hands over any channel; *Reset password* on a user row issues the same kind of link for an existing account. Link tokens are 160-bit CSPRNG values stored hashed, expire after 24 hours, and are consumed on first use; completing a reset revokes the user's other sessions, and both issuance and completion land in the audit log. The admin never sees or chooses anyone's password, and `/reset/*` lookups count against the guard's invalid-lookup budget so the token space adds no enumeration surface. (Until the panel exists in M5, the bootstrap CLI creates accounts the same way.)

Admin panel capabilities, all writing to `audit_log`: registration toggle, list/disable/enable users, search captures by user, delete any capture, set per-capture indefinite retention, browse the audit log, and view current bans/breaker state with an audit-logged **unban** action — an operational necessity (admins will ban themselves while testing links). The audit table is append-only at the database-grant level, not just by convention.

*M5 implementation notes (v0.8):*

- **Append-only is enforced by Postgres, not habit.** Migration 0002 creates a dedicated runtime role `st_app` with INSERT+SELECT but no UPDATE/DELETE on `audit_log`; compose connects the app as `st_app` and runs migrations over `MIGRATE_DATABASE_URL` (the schema-owning role). `st_app`'s password comes from `APP_DB_PASSWORD` and is re-synced at boot by the entrypoint, because a static migration file cannot carry a secret. An integration test attempts UPDATE/DELETE through an `st_app` connection and asserts `42501`.
- **Every admin mutation and its audit row share one transaction** (`writeAudit` takes the mutation's `tx`): a mid-way failure rolls both back, tested via a forced constraint violation. Audit detail carries internal row ids and 8-char secret prefixes only; the admin capture list is the one place capability URLs appear, because admins are trusted with them.
- **One-time links:** `POST /api/v1/admin/users` creates the account with an unusable random placeholder hash and returns the setup link exactly once; `POST /api/v1/admin/users/:id/reset-link` does the same for existing accounts. Consumption (`POST /api/v1/auth/set-password`) is a conditional UPDATE (first-use-wins under concurrency) that sets the argon2id hash, deletes the user's other session rows (M1's sessions are store-backed, so revocation is deletion), writes the audit row and signs the requester in — one transaction. A disabled user's link is refused *and rolled back unconsumed*, so re-enabling restores it. Multiple outstanding links per user are allowed; the 24 h TTL bounds the exposure.
- Admins cannot disable their own account (a lockout guard); disabling deletes the user's sessions in the same transaction and their API tokens die via the existing `disabled_at` join. Unchecking "Keep indefinitely" restores the default retention window anchored at `created_at` (§13). The admin unban deletes the `ip_bans` row, deliberately forgiving its strike history.
- The "Keep indefinitely" checkbox lives in the admin panel's capture list rather than on the capture page itself (§7 described the latter): admins reach any capture through search, and the capture page stays a single non-owner render. Cheap to revisit if browsing admins want it inline.

## 12. Abuse resistance

Defense-in-depth, outermost first:

**Caddy layer:** request body limit (default 30 MB, matching `MAX_UPLOAD_MB` — sized for full-page retina captures), header/timeout limits, HSTS, TLS ≥ 1.2, and a coarse per-IP request rate cap to shed dumb floods before they reach Node. *(M5 note: the rate cap is not in default Caddy builds — `deploy/Dockerfile.caddy` builds it in via xcaddy with `mholt/caddy-ratelimit` pinned to a commit, never `@latest`, since the TLS-terminating proxy is supply-chain surface; since v0.12 the same build carries the pinned `caddy-dns/cloudflare` DNS-01 provider, §14. The cap is deliberately generous — `CADDY_RATE_PER_IP_PER_MIN`, default 300/min keyed on `{remote_host}` — because the app guard above is the real enforcement layer; if the plugin ever becomes a maintenance burden, dropping it and reverting to the stock image loses nothing the spec requires.)*

**Application guard (the spec's rate limiter + circuit breaker):**

1. *Per-IP sliding windows* (keyed by IPv4 address or IPv6 /64): general unauthenticated cap (~60 req/min) and, separately, an **invalid-lookup budget** — more than 5 not-found hits on `/s/*` within 10 minutes trips a temporary ban.
2. *Escalating bans:* 15 min → 1 h → 24 h per strike, persisted in `ip_bans` so restarts don't reset them. A banned IP receives 429 for **all** `/s/*` routes — including valid links — for the duration, exactly per spec.
3. *Global circuit breaker:* if aggregate invalid-lookup rate across all IPs exceeds a threshold (e.g. 100/min — a distributed crawl signature), the breaker opens: anonymous `/s/*` traffic gets 429 + `Retry-After` for a cool-down, then half-open probes. Authenticated sessions keep working so real owners aren't collateral damage.
4. All trips and bans emit structured security events for the admin panel and logs.

*M5 guard implementation notes (v0.8):* the guard runs as one in-process module (`server/src/guard.ts`, per §2) wired in as a global `onRequest` hook, with only bans touching the database — a restart rebuilds ban state from `ip_bans` (no amnesty) but forgets in-flight windows, costing an attacker at most one fresh budget. Specifics worth knowing:

- **The ban check is in-memory and runs before any ID lookup or session resolution**, so a banned IP's 429 is byte-identical (body, headers, `Retry-After`) and timing-identical for valid and invalid links — the ban closes the oracle, not just the door. Bans and the invalid-lookup budget cover `/reset/*` as well as `/s/*`: both are secret-token surfaces and share one budget.
- **"Anonymous"** for the general cap means no *validly signed* session cookie (the signature check is cheap and unforgeable) and no bearer header. A garbage bearer header therefore skips the app-level general cap — accepted deliberately: verifying tokens in the hook would double every request's auth work, such a flood still pays full credential verification (one sha256 + indexed lookup) per 401, the Caddy-layer per-IP cap sheds it at ~300/min anyway, and the invalid-lookup budget on `/s/*`+`/reset/*` — the surface that actually guards secrets — counts every request regardless of credentials. Denied requests are not recorded, so windows are memory-bounded; distinct-key maps are capped with oldest-activity eviction.
- **Strikes live in the `ip_bans` row and outlive `banned_until`**, so waiting out a ban never resets escalation; the ladder (`RATE_BAN_LADDER_MINUTES`, default 15,60,1440) clamps at its last rung. Expired rows are kept for their strike history; the admin unban deletes the row, which deliberately also forgives the strikes.
- **Breaker state machine:** closed → open (`RATE_BREAKER_COOLDOWN_SECONDS`, default 300) → half-open on the first check after cool-down. Half-open re-opens when invalid lookups reach ceil(threshold/10) (min 1), and closes after a clean minute. While open, anonymous blocked traffic is refused before lookup and therefore does not feed the aggregate window; authenticated invalid lookups still count against their IP's budget.
- **Client IP derivation:** `TRUST_PROXY` accepts `true`/`false` or a CIDR list; compose pins it to the fixed `web` network subnet (172.28.101.0/24) so only Caddy can assert `X-Forwarded-For` — a spoofed header from anywhere else is ignored and the socket address is keyed instead. IPv6 clients are keyed by /64; IPv4-mapped addresses unwrap to their IPv4 form.
- Server-side faults (a live row whose image file is missing) return the same uniform 404 but never count against a budget — misconfiguration must not ban innocent viewers.

**Upload pipeline hardening:** bearer-token required → magic-byte sniffing (PNG/JPEG only, never SVG) → decode with `sharp` under `limitInputPixels` plus explicit dimension caps (≈10,000 px wide, 32,000 px tall, ~150 MP total — decompression-bomb guard sized to admit the largest legitimate full-page capture, §15) → re-encode to PNG, which strips metadata and neutralizes polyglot files → write with server-chosen name. `source_url` must parse as `http(s)` and is length-capped; `page_title` is length-capped and escaped on output.

**Browser-facing hardening:** strict CSP (`default-src 'self'`; no `unsafe-inline`, no `unsafe-eval` — Vite is configured accordingly), `frame-ancestors 'none'`, `X-Content-Type-Options: nosniff`, and images served with correct `Content-Type` + `Content-Disposition: inline`. Re-encoding on ingest means stored images can't smuggle active content even if a browser mis-sniffed.

**Container hardening:** app image built distroless (or Alpine with no shell), runs non-root with `read_only: true` and a tmpfs for scratch; Postgres unexposed on an internal network; resource limits on every service; `no-new-privileges`; Trivy scan in CI. Secrets come from `.env` (never committed); session secret and DB password are generated at install.

**Operational:** nightly `pg_dump` + restic (or rsync) of the image volume to off-box storage; pino JSON logs with security events tagged for alerting; `npm audit`/Dependabot in CI.

*M7 operations notes (v0.10):*

- **Security events are one namespace.** Every security-relevant occurrence — ban created/expired/lifted, breaker opened/half-open/closed, general and login throttle trips, every authentication and authorization failure, every admin mutation (logged after its audited transaction commits, so a log line never exists without its audit row), purge runs and server-side faults — is emitted through one helper as a pino line with `tag: "sec.<area>.<event>"` at a fixed level (`server/src/security-events.ts`, catalogue in `docs/security-events.md`; a unit test fails when a tag lacks a doc row). Redaction covers credential headers and secret-shaped keys one level deep on top of the 8-char path truncation. `TRUST_PROXY=true` (or a `/0` CIDR) logs `sec.proxy.permissive_trust` at error level on every boot — expected only under the loadtest profile.
- **Backups (`deploy/backup/`).** A sidecar built on the database's own `postgres` image tag (pg_dump matches the server major; the pin in `deploy/docker-compose.yml` is authoritative and `scripts/check-image-pins.sh` holds the sidecar, CI and verify-restore to it) runs nightly: custom-format dump with ACLs kept plus a row-count manifest, a hardlinked `rsync` snapshot of the image volume, rotation after `BACKUP_KEEP_DAYS`, and — when `RESTIC_REPOSITORY`/`RESTIC_PASSWORD` are set — a restic snapshot with a keep-daily/weekly/monthly policy. Without restic the backup stays on the same disk and says so in its log. `verify-restore.sh` restores the latest dump into a scratch Postgres (creating the cluster-level `st_app` role first, as a real restore must), compares row counts, checks `audit_log` is still append-only for `st_app`, and restores one image and verifies its sha256 against the restored row; both the local and the restic path were run green in M7. Roles are not in a database dump: the restore runbook in `deploy/README.md` creates `st_app` before `pg_restore`.
- **k6 guard load test (`pnpm loadtest`, `docs/loadtest.md`).** Runs against a separate compose project (`deploy/docker-compose.loadtest.yml`: fresh volumes, `TRUST_PROXY=true` so k6 can assert virtual client IPs, breaker cool-down shortened to 30 s, Caddy and the backup sidecar parked behind profiles). Three scenarios with thresholds: single-IP enumeration is banned after exactly budget+1 misses while a second IP's valid link stays 200; a 150-IP crawl opens the breaker (anonymous valid links 429 + `Retry-After` ≤ cool-down, the owner's session unaffected), recovery is observed after the cool-down and the breaker is asserted `closed` in teardown; and a 30-viewer baseline with p95 budgets on the page and image routes. k6 is a container, not a dependency, and stays out of default CI. No production guard default needed tuning.
- **Supply chain in CI.** `pnpm audit --audit-level=high` (reviewed ignores in `package.json` `pnpm.auditConfig`, reasons in `docs/supply-chain.md`), Trivy on the built app, backup and Caddy images (HIGH/CRITICAL with a fix fail; `deploy/.trivyignore` for reviewed exceptions), and grouped weekly Dependabot (one PR per ecosystem for version updates; security updates stay one PR each) with majors excluded from automation where a bump is really a migration: Fabric.js/sharp/argon2/Fastify, TypeScript and `@types/node` (they move with the toolchain and the runtime major), and the `postgres` image (a dump/restore per `deploy/README.md`). The images upgrade their base OS at build time; the app runtime drops npm/corepack/yarn, the backup image drops `gosu`, and Caddy is built from an exact patch release with Go modules bumped where a release still pins vulnerable ones.

## 13. Retention and lifecycle

`retention_until = created_at + RETENTION_DEFAULT_DAYS (30)` on upload. Owners can raise it up to `RETENTION_MAX_DAYS_USER (365)` from the capture page (M3: `PATCH` with `retentionDays`, always anchored at `created_at`; beyond the ceiling → 400); admins can clear it (indefinite) via the checkbox. An hourly job deletes expired originals and flat renders, tombstones the rows (§5), and hard-deletes tombstones after `TOMBSTONE_DAYS` (90). Expired links fall into the uniform-404 behavior of §6.

*M7 purge notes (v0.10):* the job (`server/src/jobs/purge.ts`) is in-process on the injected clock like the guard, runs once at boot and then hourly, and is single-flight. One pass is three idempotent steps: expire (files unlinked, then `deleted_at` set and annotations cleared — attribution stays per §5; `retention_until IS NULL` is never selected), sweep (every tombstone, including owner and admin deletes, has its files unlinked again so a failed unlink at delete time converges), and hard-delete (tombstones with `deleted_at` older than `TOMBSTONE_DAYS`, files first). Files go before rows so a crash never leaves a tombstone with a live file; a row is skipped — never half-processed — when its unlink fails, and is retried next pass. The reverse gap (live row, file gone) is closed by the image route: the flat renderer reports a missing original as "gone" and the route answers the uniform 404 without charging the guard (`sec.image.missing_file`). The lifecycle equality test covers never-existed, owner-deleted, expired-and-purged, hard-deleted, missing-file (plain and annotated) and malformed, all byte-identical.

## 14. Deployment, TLS, configuration

`docker-compose.yml` with three services — `caddy` (one published port, `PUBLIC_PORT`, TCP + UDP; volumes for ACME state), `app`, `postgres` — plus the `backup` sidecar (M7), named volumes for images and DB data, healthchecks, and `restart: unless-stopped`. Caddy's site block is `{$PUBLIC_HOST}:{$PUBLIC_PORT} { tls { dns cloudflare {env.CLOUDFLARE_API_TOKEN} } reverse_proxy app:3000 }`, which gives automatic Let's Encrypt issuance and renewal through the DNS-01 challenge — nothing listens on 80 or 443 (v0.12 notes at the end of this section; the original design used HTTP-01 with port 80 open for the challenge and redirects); it also imports `deploy/caddy.d/*.caddy`, whose one intended content is the old-domain redirect during a migration (§15). *M8:* the `postgres` image is pinned to an explicit patch tag (`16.15-alpine`, one authoritative literal in compose, enforced across every other site by `scripts/check-image-pins.sh`) rather than the floating `16-alpine`: `up -d --build` never re-pulls a cached floating tag, so a floating pin meant silent staleness that Dependabot could not even propose a fix for; the explicit pin gives reproducible deploys and a visible `16.N → 16.N+1` PR trail (majors stay ignored — they are a dump/restore migration per `deploy/README.md`).

*v0.12 TLS and network posture notes (2026-09-01):*

- **DNS-01 instead of HTTP-01.** `deploy/Dockerfile.caddy` builds Caddy with `github.com/caddy-dns/cloudflare` (pinned tag, `CADDY_DNS_MODULE` build arg so a provider swap is a one-arg rebuild plus one Caddyfile line) next to the rate-limit plugin; the image is Trivy-scanned in CI like the app and backup images. The site block's `tls { dns cloudflare {env.CLOUDFLARE_API_TOKEN} }` makes certmagic register the DNS solver *exclusively* (verified in its source: with a `DNS01Solver` set, no HTTP-01 or TLS-ALPN-01 solver is created), so issuance and renewal never need an inbound connection; `auto_https disable_redirects` removes the only other thing that would bind :80. Adapting both Caddyfiles confirms a single `:28443` listener and no `http_port`/`https_port`; the running container shows only 28443 (TCP + UDP) plus the loopback admin endpoint. Renewal therefore depends on the token remaining valid — an operational fact `deploy/README.md` states plainly, together with the least-privilege token recipe (Zone:Read + DNS:Edit on one zone; DNS:Edit alone fails the plugin's zone lookup) and the requirement that the record be DNS-only (grey cloud): Cloudflare's proxy forwards only a fixed set of ports and terminates TLS with its own certificate.
- **One high port, honestly framed.** The service listens on `PUBLIC_PORT` (28443) and the host opens nothing else. This is conflict avoidance (nothing else on the box or IP contends for 80/443) and surface reduction (two well-known listeners fewer), **not** security: mass scanners sweep every port, and the design's defenses — the 160-bit capability URLs (§6), the guard (§12) and the strict headers — are unchanged and identical on any port. No document in this repo may imply otherwise. 28443 sits below Linux's default ephemeral floor (32768), so the listener needs no port reservation on the host.
- **Configuration stays one-variable, drift fails loudly.** `PUBLIC_ORIGIN` remains the single source of every generated URL — capture page and image links, admin one-time links, `/ext/updates.json` and its artifact link, the Firefox `update_url` — and compose derives it as `https://$PUBLIC_HOST:$PUBLIC_PORT`, so every URL inherits the port with no per-route code. The app additionally receives `PUBLIC_PORT` and refuses to boot if the origin's effective port differs (unit-tested in `config.test.ts`, exercised in `server/test/integration/ported-origin.test.ts`), in the same spirit as the image-pin check. The extension build derives the same origin from `deploy/.env` (`extension/scripts/lib/env.ts`), bakes it as the default server, and the release audit accepts a ported production origin while still refusing loopback and placeholder origins with a port. No manifest change was needed: the Chrome host pattern keeps the explicit port, Firefox's matcher ignores ports, and the port-less `optional_host_permissions` pattern matches every port in both browsers (comments in `extension/src/lib/origin.ts` and `manifest.ts`).
- **Local development is untouched:** `pnpm dev` on bare Fastify (`PUBLIC_ORIGIN=http://localhost:3000`) is unchanged, and the compose path is `https://localhost:28443` under Caddy's internal CA via `docker-compose.local.yml` — now required for `localhost` too, because the explicit DNS-01 issuer in the production Caddyfile overrides Caddy's internal-CA default for local names (confirmed by adapting the Caddyfile: `localhost` received an ACME issuer). The migration rehearsal (`deploy/test-domain-migration.sh`) runs on the custom port and asserts the port survives the 308 and that nothing in the proxy listens on 80/443; it keeps the internal CA because real DNS-01 needs a real zone and token. Real Let's Encrypt issuance through DNS-01 was not exercised in development and is the owner's first-boot check.
- **Deliberately out of scope:** a multi-site or shared-edge Caddy (a different problem — the edge would own certificates, ports and the client IP the guard keys on), a TLS-ALPN-01 fallback, and any listener on 80 or 443.

## 15. Extension design (Chrome + Firefox)

One TypeScript codebase, Manifest V3 on both browsers, built with Vite + `webextension-polyfill`. Chrome uses a background service worker; Firefox uses a non-persistent event page — a build step emits `manifest.chrome.json` / `manifest.firefox.json` from a shared template, which is the only per-browser difference.

**Permissions (deliberately minimal):** `activeTab` (grants capture and injection rights on the invoked tab without `<all_urls>`), `scripting` (injects the region-select overlay and the full-page scroll driver), `storage`, `notifications` (the only way to report an upload failure once the popup has closed or when the trigger was a shortcut — added in M2), plus a `host_permissions` entry for the build-time default server and `optional_host_permissions: ["https://*/*"]` so pointing the extension at a new domain triggers a one-time permission prompt for just that origin. Restricted pages (`chrome://`, `about:`, extension pages, the extension stores, and anything without an http(s) address, which the server would refuse as `source_url` anyway) can't be captured or injected; the popup detects this up front, disables capture and says why.

*M2 findings that shape the above:* Chrome's `captureVisibleTab` accepts only `activeTab` or `<all_urls>` — a specific host permission is not sufficient — so capture always rides on the toolbar/shortcut gesture and cannot be driven by automation without one (see `extension/TESTING.md`). Firefox treats every MV3 host permission as optional (not granted at install), and supports `optional_host_permissions` only from Firefox 128, which is therefore the minimum version; the options page requests the host permission for exactly the entered origin on Save and Test connection (Chrome grants the built-in default silently, Firefox prompts once, custom domains prompt on both). A denied request leaves the settings untouched. Because runtime grants are limited to `https://*/*`, a plain-http server can only ever be the build-time default (`PUBLIC_ORIGIN=http://localhost:3000` for local development). Firefox additionally ignores ports in match patterns (bugs 1362809/1468162 — the pattern is accepted, `permissions.request` succeeds, but nothing ever matches), so the Firefox manifest and its runtime permission requests use port-less host patterns (`http://localhost/*`), which in Firefox match every port on that host; Chrome keeps the exact origin with its port.

**Mode selection:** the toolbar button opens a three-button popup — Visible / Region / Full page — and each mode also gets its own configurable keyboard command. The popup highlights the last-used mode (`storage.local`). M2 ships the layout with Region and Full page disabled ("coming in M6") and declares only the `capture-visible` command (default `Alt+Shift+S`); M6 enables the buttons and adds the other two commands without changing the layout.

**Visible viewport:** `captureVisibleTab({format:"png"})` → blob → upload. This is the M2 walking skeleton. The flow runs in the background (service worker / event page), not the popup, so closing the popup never aborts an upload; the popup just relays the result while it is open.

**Region selection:** a content-script overlay dims the page and lets the user drag a rectangle (Esc cancels). The overlay returns the rect in CSS pixels plus `devicePixelRatio`; the background captures the visible tab once and crops via `createImageBitmap` + `OffscreenCanvas` (available in Chrome's service worker; Firefox event pages have a DOM canvas), so the stored image is exactly the selection.

**Full page — two strategies, because the browsers differ:**

- *Firefox:* `tabs.captureTab(tabId, { rect })` accepts page coordinates beyond the viewport, so the whole document is captured natively in one call — no scrolling, no stitching, no artifacts.
- *Chrome:* has no equivalent short of the `debugger` API (scary permission, store-review friction, an on-screen "being debugged" banner), so Chrome scroll-and-stitches: a content script measures the document, scrolls in viewport-height steps, and the background captures each tile onto an `OffscreenCanvas`. Known hazards and their mitigations: Chrome throttles `captureVisibleTab` to roughly 2 calls/sec, so tiles are paced ~600 ms apart, which also gives lazy-loaded content time to settle; `position: fixed`/`sticky` elements would repeat in every tile, so after the first tile the driver temporarily sets them `visibility: hidden` and restores them afterward; all geometry is scaled by `devicePixelRatio`.
- *Both:* capture height is capped at ~32,000 physical px (browser canvas limits and editor sanity — §9); a longer page yields the top slice plus a notice. Scroll position and any hidden-element tweaks are restored even on error, via a `finally` path in the driver.

**Upload + errors:** the produced PNG posts to `${server}/api/v1/captures` (multipart, fields from `shared/` `CAPTURE_UPLOAD_FIELDS`) with the bearer token and `{sourceUrl: tab.url, title: tab.title}`, `credentials: 'omit'` and no redirect following; the returned `pageUrl` (accepted only if it is an http(s) URL) opens in a new tab next to the source. Failures surface two ways, because a notification alone proved insufficient in M2 testing (macOS Focus / muted browser notifications swallow it silently, and on the keyboard-shortcut path there is no popup to fall back on): a browser notification, plus a red `!` badge on the toolbar icon with the message as its tooltip and the message stored as `lastError` in `storage.local`; the popup shows that stored error once on next open and clears badge and store, and a successful capture clears both as well (no extra permission — `action.setBadgeText`/`setTitle`). A 401 — or no token configured yet — additionally opens the options page. The token is read from `storage.local` for the request and never logged or echoed in any message.

**Options page:** server origin (pre-filled from `PUBLIC_ORIGIN` at build time; validation fails closed — bare http(s) origin only, https required except for `localhost` / `127.0.0.1` / `[::1]`), API token (stored in `storage.local`, deliberately *not* `storage.sync`, so the secret never transits sync infrastructure), and a "Test connection" button that calls `GET /api/v1/ping` (§8) with the bearer token: 204 → connected, 401 → token rejected, otherwise the transport error, never the token.

*M6 findings that shape the above (v0.9):*

- *Firefox `captureTab` scale.* Measured on Firefox 154 with a throwaway MV2 probe (`docs/firefox-capturetab-probe.md`): the output is exactly `rect × scale`; `scale` is an absolute physical-px-per-CSS-px factor that **defaults to** `devicePixelRatio` and is not multiplied on top of it, so the extension passes `scale: devicePixelRatio` explicitly for a deterministic size. Firefox neither clamps nor refuses tall rects (40,000 rows render; a rect taller than the document is padded), so the 32,000-physical-px cap is enforced by us: the requested rect is capped at `floor(MAX_IMAGE_HEIGHT_PX / scale)` CSS px **and** the decoded result is re-measured and cropped if a future browser scales differently. `resetScrollPosition: true` renders fixed elements once, at the top. Firefox event pages do have `OffscreenCanvas` (since 105); the canvas helper uses it where present and falls back to a DOM canvas.
- *Region is two-phase.* Chrome's service worker may be recycled while the user is still dragging (a pending `tabs.sendMessage` keeps it alive for at most five minutes), so the content script answers the select command with `started` immediately and sends the result as a fresh `runtime.sendMessage`, which wakes the worker; the handler re-derives tab, settings and permissions from the sender rather than from memory. Capture requests are accepted only from the extension's own pages (matched on `sender.url`, because Chrome populates `sender.tab` for extension pages opened in tabs), region results only from a content script in a real tab, and every payload is validated (`lib/content-protocol.ts`).
- *Overlay isolation.* The overlay is a custom element attached to `<html>` (not `<body>`, whose transforms break fixed positioning) with a **closed** shadow root and every host property set inline `!important`, which outranks stylesheet `!important` — the hostile-CSS fixture in `extension/test/browser/` pins this. Pointer/mouse/click events are stopped at the host so bubble-phase page listeners never see them; capture-phase listeners on `window`/`document` cannot be suppressed (platform behaviour). The host is focused so Esc reaches the overlay even when an iframe had focus, and two animation frames are awaited after removal before the capture fires.
- *Stitch geometry* lives in `extension/src/lib/capture-geometry.ts`, pure and exhaustively unit-tested: tiles are `documentElement.clientHeight` apart; the last tile scrolls only to `documentHeight − viewportHeight` and is crop-composited from `srcY = destY − scrollY`; the composite is `clientWidth × scale` wide so classic scrollbars never stripe the right edge; physical edges are rounded from CSS *edges*, never from heights, so fractional scales (1.25, 1.5) meet without seams; the scale is derived from the first tile actually returned (`image.width / innerWidth`) rather than trusted from the page. Where the page lands somewhere other than requested (it shrank, grew, or snapped), `drawRectFor` intersects the wanted rows with the shown rows and draws only those. The first tile is captured before fixed/sticky elements are hidden; hiding uses inline `visibility: hidden !important` and restores the exact prior inline value.
- *Cleanup and cancellation.* The driver restores scroll and hidden elements in a `finally` on success, throw, rejection, Esc, or tab switch; the stitcher checks `tabs.get(tabId).active` before every tile because `captureVisibleTab` captures whatever tab is visible. The content script additionally arms a 15 s watchdog that restores the page if the background falls silent. A single in-memory lock refuses a second capture while one runs and is released when a region result arrives or the pending tab navigates away or closes. Progress goes on the action badge as a percentage.
- *Known limitations, documented in `extension/TESTING.md` §7 rather than fixed:* inner scroll containers (only the window's scrolling element is driven — deliberately out of M6); sticky elements whose natural position is below the first viewport are hidden with the rest; closed shadow roots cannot be searched for fixed elements; lazy content is captured at the height measured when the run started.

**Domain migration** is therefore: change `PUBLIC_HOST` in `.env` → add the old-domain `redir 308` block in `deploy/caddy.d/` (same `PUBLIC_PORT`, same DNS-01 snippet; the precondition since v0.12 is that the API token can edit the new name's zone — no port opens or closes) → `docker compose up -d` (Caddy obtains the new cert through DNS-01, both stay live) → `build:release` and re-sign/republish the extension (new baked-in default, port included). Keep the old domain's redirect for at least `RETENTION_MAX_DAYS_USER` so previously shared links keep resolving — and, if indefinite-retention captures exist, either permanently or with accepted breakage on a chosen date; users who overrode the server in options just update one field and accept the one-time host-permission prompt. The full procedure, its verification and rollback are `docs/runbooks/domain-migration.md`; `deploy/test-domain-migration.sh` rehearses it against a throwaway compose project on the custom port and asserts that `/s/<id>?query` survives the 308 byte-for-byte, port included, and that the proxy listens on nothing but `PUBLIC_PORT` (M8, v0.12).

*M8 packaging and distribution notes (v0.11):*

- **One version, two audited artifacts.** `pnpm --filter extension build:release` builds both targets with `extension/package.json`'s version stamped into both manifests and the deployment's `PUBLIC_ORIGIN` (from `deploy/.env`) baked as the default server, then audits `dist/<target>` and the zip: the manifest must equal the template-generated one for those inputs (templates-only, no hand edits), no file may contain `http://`, a loopback host (except the options page's own help text about localhost), a placeholder host, `console.log/debug/info`, `debugger`, a source-map reference or `process.env`; no `.map`/`.ts`/dotfiles ship; and the zip must be exactly the directory. addons-linter then runs over the Firefox build in self-hosted mode with warnings as errors. The build refuses the placeholder origin, a loopback origin and a missing `EXTENSION_GECKO_ID`. The first audit run found TypeBox (with a `URL.canParse(…, 'http://example.com')` in its format code) in every bundle — `shared`'s barrel builds schemas at import time and Rollup cannot drop them — so the extension imports only `@snapping-turtle/shared/constants` (and `CAPTURE_UPLOAD_FIELDS` moved there); background.js shrank by an order of magnitude.
- **Firefox floor is 140.0 (Android 142.0), up from 128.** AMO requires `browser_specific_settings.gecko.data_collection_permissions` for new submissions; Firefox understands the key from 140 (Android 142) and addons-linter flags it as unsupported below that. 128 ESR reached end of life before M8, and 140 is the current ESR, so nobody real is excluded. The declaration is `required: ["websiteContent", "browsingActivity"]` — the truthful categories for "screenshots plus the page URL and title, sent to the user's own server"; there is no "none" to claim. Android is declared compatible but untested (`extension/TESTING.md`).
- **Self-hosted updates complete decision A4 (scope addition).** A self-distributed Firefox extension does not update by itself, so the Firefox manifest (only) carries `update_url: <PUBLIC_ORIGIN>/ext/updates.json` (port included since v0.12) — omitted for a plain-http localhost dev build, because Firefox requires https there — and the app serves `EXT_DIR` read-only at `/ext/`: exactly `updates.json` and `snapping-turtle-firefox-<version>.xpi`, no listing, no other file shapes, `Cache-Control: public, max-age=300`, the usual security headers. The route is public and secret-free by construction: the artifacts are what AMO signed and Firefox verifies both the signature and the `sha256:` in `updates.json`. Chrome has no update_url — the Web Store updates it.
- **Signing is env-gated and local.** `pnpm --filter extension sign:firefox` drives `web-ext sign` on the unlisted channel with `WEB_EXT_API_KEY`/`WEB_EXT_API_SECRET` read by web-ext from the environment (never argv, never a file, never printed), then copies the signed `.xpi` into `deploy/ext/` and upserts `updates.json` (ascending versions, sha256, `strict_min_version`); `--xpi <file>` publishes an already-signed file when AMO's queue held a version. The add-on id is pinned by `EXTENSION_GECKO_ID`, required for release builds, because AMO ties every later version to the id of the first signing and the M2 default (`snapping-turtle@<hostname>`) would have changed with a domain migration and orphaned every installed copy. `web-ext` is a dev dependency (lint + sign); its transitive `image-size` CVEs are reviewed exceptions (`docs/supply-chain.md`).
- **The home page offers both builds (E2, 2026-09-02).** `GET /` is server-rendered from what exists at request time: the Firefox card links `GET /ext/firefox-latest`, a 302 to the newest `.xpi` named in `updates.json` (highest version numerically, its file checked to exist — otherwise the route is a plain 404 and the card says "not yet published" rather than linking a dead download), so the page never rots as versions ship and needs no rebuild; the Chrome card links `CHROME_EXTENSION_URL` (§14) once the listing is approved and says "coming soon" until then. Both cards always render; the bundle adds a "your browser" badge to the visitor's card from the user agent (Chromium family counts as Chrome) and never hides the other. The filename in the redirect derives from the version, not from `update_link`, so it stays same-origin across a domain migration. The parser for `updates.json` moved to `shared/src/firefox-updates.ts` so the signing script and the server read one definition.
- **Chrome is a human-gated handoff.** `extension/STORE_SUBMISSION.md` carries the unlisted-listing checklist, drafted copy, per-permission justifications, the data-use disclosure (website content, web history, authentication information — all sent only to the user's own server) and a privacy-policy text to host. Nothing in the repo can submit; the release workflow (`.github/workflows/release.yml`, on `v*` tags) builds and attaches both zips to a GitHub release and deliberately does not sign.

## 15a. Native Linux client (M9)

A resident desktop app for Fedora 44 / KDE Plasma 6 / Wayland (`client-linux/`, Rust): tray icon with a three-entry capture menu, desktop-file actions for the same three modes, portal global shortcuts, upload with the personal API token, and the capture page opened in the system browser. It is a peer of the extension on the upload API and shares nothing else with it; PLAN sections it touches are §5/§7/§8 (nullable `source_url`), §12 (client-side size checks mirror the ingest caps) and §17 (what was deliberately not built).

**Capture APIs — two, and nothing else.** Primary: `org.freedesktop.portal.Screenshot` through ashpd — portable, consent handled by the desktop, the only path on GNOME. Secondary, KDE-native: KWin's `org.kde.KWin.ScreenShot2` (v5 on Plasma 6.7), authorised via `X-KDE-DBUS-Restricted-Interfaces=org.kde.KWin.ScreenShot2` in the installed desktop file — KWin resolves the caller's `/proc/<pid>/exe` to a desktop file whose `Exec` names it, so the annotation only works for the installed binary and a build-directory copy falls back to the portal. No custom selection overlay, no grim/slurp or other compositor paths (§17). The portal path is untouched by the KDE one, so GNOME keeps working; Plasma is the verification target.

**Measured on Fedora 44 / Plasma 6.7.4 / xdg-desktop-portal 1.22.1 (2026-09-03; details and the per-mode table in `client-linux/README.md`):**

- The KDE portal backend's non-interactive `Screenshot` is KWin `CaptureWorkspace` — every output stitched (5,120 px wide on the two-monitor desk here; a three-monitor desk exceeds the 10,000 px ingest cap) — **saved to `~/Pictures/Screenshot_<yyyyMMdd_hhmmss>.png`**, not a temp dir, and gated by the frontend's `screenshot` permission (an access dialog on first use per app id, remembered in the permission store). Its interactive dialog offers *Full Screen / Current Screen / Active Window* with cursor and border toggles and a preview — **no rectangular region** — and never prompts for permission (the dialog is the consent).
- KWin ScreenShot2 streams raw pixels over a pipe with `format`/`width`/`height`/`stride` in the reply; on this session `CaptureActiveScreen` returned 5120×1440 as QImage format 6 (ARGB32 premultiplied), converted and PNG-encoded in-process — no file, no dialog. `CaptureInteractive(kind=window)` shows KWin's crosshair and hint; `CaptureArea` takes coordinates only; there is no area kind.

**Per-mode decision:** *Full screen* → KWin `CaptureActiveScreen` (the active output at native resolution, silent), portal non-interactive elsewhere. *Window* → KWin `CaptureInteractive(window)` (click the window; unambiguous from a tray or a shortcut, unlike "active window"), portal interactive elsewhere. *Region* → the portal's interactive chooser on every desktop: it is the only sanctioned path that offers a rectangle anywhere (GNOME's UI does; Plasma 6.7's does not), and it starts offering one on Plasma the day xdg-desktop-portal-kde adds it, with no client change. The three are genuinely distinct flows on Plasma; the Plasma region gap is recorded honestly in the README, TESTING.md and §17 rather than papered over with an overlay or a Spectacle call.

**Upload and open:** the PNG posts to `POST /api/v1/captures` as multipart `image` + `title` (`<Mode> <local date time>`), bearer token, **no `sourceUrl`** (§8); the client refuses locally what ingest would refuse — over `MAX_UPLOAD_MB`, wider than 10,000 or taller than 32,000 px — before spending the upload; 201's `pageUrl` (http(s) only, like the extension's check) opens via OpenURI; every outcome is a portal notification, 401 naming `--configure`. TLS is rustls through the platform verifier, so the real Let's Encrypt certificate on `PUBLIC_PORT` verifies from the system trust store. Redirects are never followed with the token attached.

**Identity.** One reverse-DNS app id (`CLIENT_APP_ID`, pinned in `deploy/.env` like `EXTENSION_GECKO_ID`, baked in at build with a development default) names the desktop file, the resident DBus name, the notification source and the autostart entry, and is registered with the portal on startup through `org.freedesktop.host.portal.Registry` (harmless when the launcher's systemd scope already identified us). The portal keys the remembered screenshot grant, the shortcut bindings and the background decision on it: one value everywhere, never changed after the first install (`client-linux/src/app_id.rs`). A second launch and every desktop action forward to the resident instance over a small control interface so there is one tray icon and one shortcut session.

**Secrets (rule 3 across the language boundary).** The token lives in the Secret Service keyring (ksecretd/KWallet on Plasma) or, when none answers, in a 0600 file in the 0700 config directory; the JSON config records only the origin and which store. Stderr, notifications and the tray tooltip carry tokens and capture URLs as 8-character prefixes; `--print-url` is the explicit scripting exception on stdout.

**File hygiene.** The KWin path never writes. For the portal path the client removes exactly the returned path, only when it is a regular `.png` modified no earlier than the request started — the user's own screenshot copies (Spectacle's `~/Pictures/Screenshots/`) are older and untouched. Ten captures leave `~/Pictures` unchanged (TESTING.md item 12; the full-screen half measured here).

**Autostart** is offered at `--configure` (default on for a tray app) through the Background portal, which writes `~/.config/autostart/<app id>.desktop` for a host app and removes it on disable; `--autostart off` reverses it, and the client writes or removes the same entry itself if the portal cannot.

**Tests.** `cargo test` covers the pure parts (QImage→RGBA→PNG for every format KWin emits, cleanup rules, config/token files and modes, origin normalisation, response classification, redaction, argument parsing) and reads `shared/src/constants.ts` to hold the mirrored constants; `client-linux/scripts/integration.sh` boots the real server from `server/test/helpers/client-harness.ts`, configures the binary non-interactively, uploads the fixture, and asserts the row (`source_url` NULL, title, dimensions, token attribution), the page (no source link, preview tags), the image, and that neither the token nor the capability id leaks into the client's output — in CI on every push. Portal and tray behaviour that needs a session is the human's checklist (`client-linux/TESTING.md`). CI checks the crate in a `fedora:44` container (fmt, clippy `-D warnings`, test, release build, RPM build and install — every cargo call `--locked` against the committed `Cargo.lock`, on the compiler `client-linux/rust-toolchain.toml` pins and `scripts/toolchain.sh` installs through rustup; the distro's rustc is never used, because its version moves with the updates repo and clippy's lint set moves with it); the release workflow attaches the RPM and the raw binary.

## 17. Future considerations (deliberately deferred)

Nothing here is planned; each item is recorded so a future change starts from the reasoning rather than rediscovering it.

**The §2 questions deferred 2026-09-01 (M8) — two remain; the third, Open Graph previews, was resolved by E3 on 2026-09-02 (§6):**

- *Abuse-report button for viewers.* Not needed for a friends-only deployment where the admin knows every uploader and every capture is attributed (owner, token, IP) and searchable per user in the admin panel; a takedown is "delete any capture" plus "disable user", both audited. A report button would add an anonymous write surface under `/s/*` — the one place the design keeps free of anything but reads — and needs a triage inbox to be meaningful. Revisit if the deployment ever admits uploaders the admin does not know.
- *Owner toggle to hide the source-page link.* The spec requires the link and the link is the feature's second half; internal-URL leakage is real but is bounded by the capability URL itself (whoever has the link already has the screenshot). Cheap to add (a boolean column, a checkbox, two renderers), deferred because no user has asked and every optional field on the capture page is one more thing the flat renderer and the uniform 404 must not distinguish on.
- *Per-capture link-preview opt-out (noted at E3, 2026-09-02).* Previews are on for every live capture page (§6). An owner who wants a particular link to unfurl as a bare URL — say, a capture whose title alone is sensitive in a group chat — would need a boolean on the row, a checkbox on the editor page, and the tags omitted when set. Not built: nobody has asked, and every optional field on the capture page is one more thing the uniform 404 must not distinguish on (the tagless page must still be a *valid* page, not a third response shape). If built, omit only the tags — never vary status, headers or the 404.

**Per-shape user-adjustable stroke width (noted at E1, 2026-09-02):** E1 made every size a function of the capture width and kept the wire format at schema v1. Letting an owner thicken or thin one shape means a new optional field per shape (a stroke multiplier or an absolute width), a schema version bump with a migration path for v1 documents, a control in the editor, and the same field honoured by the SVG renderer with new parity fixtures — the "different, larger change" E1 stopped short of. Start from `annotationSizes()` as the default and store only deviations from it.

**Linux client follow-ups (noted at M9, 2026-09-03):**

- *Flatpak packaging.* Likely the better long-term distribution (sandboxed, portal-native, one artifact for every distribution) and deliberately second: the RPM proves the design on the target machine first. A Flatpak changes three things the RPM does not have to think about — the app id must match the Flatpak id, KWin's ScreenShot2 authorisation keys on the host executable path and is unavailable inside the sandbox (full screen and window would fall back to the portal), and the token store becomes the Secret portal's file keyring (oo7 handles it). Start from the RPM's desktop file and `ashpd::is_sandboxed()`.
- *Rectangular region on Plasma.* Neither sanctioned API offers one on Plasma 6.7 (§15a). Options, in order of preference: wait for xdg-desktop-portal-kde to grow a region entry in its chooser (the client already calls that path); a Spectacle delegation (`org.kde.Spectacle` DBus, a third API); a custom layer-shell overlay feeding KWin `CaptureArea` — the overlay the design rejected. Do not add grim/slurp or any wlroots path: they are compositor-specific and the two sanctioned APIs already cover Plasma and GNOME.
- *GNOME verification and polish.* The portal path keeps working unmodified and the desktop actions and shortcuts cover the tray's absence, but nothing on GNOME was exercised this milestone: the AppIndicator-extension tray, GNOME Shell's chooser for window and region, its permission prompt wording. macOS and Windows clients are separate designs, not ports.
- *In-client annotation UI.* Never: the browser page is the editor by design; the client's job ends at opening it.

**Scaling and platform:** S3/object storage and Redis-backed guard state for multi-node; separately rotatable image-only tokens; invite codes; email + password reset; WebAuthn/2FA for admins.
