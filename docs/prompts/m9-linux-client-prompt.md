This session's scope is **M9: a native capture client for Fedora 44, KDE Plasma, Wayland** — resident app with a tray icon, whole-screen / region / window capture, upload with the bearer token, then the annotation page opens in the system browser. Design decisions, made:

- **Capture uses two sanctioned APIs and nothing else.** Primary: the XDG Desktop Portal (`org.freedesktop.portal.Screenshot`), portable and consent-handled by the compositor. Secondary, KDE-native: KWin's `org.kde.KWin.ScreenShot2` DBus interface — which offers genuinely distinct full-screen / window / interactive capture — authorized via the `X-KDE-DBUS-Restricted-Interfaces` annotation in the installed desktop file. Verify empirically what Plasma 6's portal implementation actually delivers per mode on Fedora 44, and use ScreenShot2 to fill the gaps it leaves. Do not build custom selection overlays and do not add other compositor paths (grim/slurp → §17). The portal path must keep working unmodified so GNOME users aren't broken, but Plasma is the verification target.
- **Language: Rust** — the repo's first documented exception to TypeScript-everywhere. Rationale to record in CLAUDE.md: `ashpd` is the maintained first-class portal binding, the output is a single dependency-light binary, and this component shares nothing with the renderer code where the shared-types rule matters.
- **The tray is first-class here:** Plasma supports StatusNotifierItem natively, so the tray icon and its menu are the primary surface — complemented by desktop-file actions for each mode and portal GlobalShortcuts, which Plasma 6 implements with a proper grants UI. (On GNOME the tray needs the AppIndicator extension; the actions-and-shortcuts path covers that case, documented but not verified this milestone.)

## Definition of done — verify each item by running it, not by assertion

1. **Workspace + toolchain:** `client-linux/` Rust crate; CLAUDE.md gains the layout entry, the commands (`cargo fmt --check`, `cargo clippy -- -D warnings`, `cargo test`, `cargo build --release`), and the language-exception note. CI runs those in a `fedora:44` container; the release workflow additionally packages and attaches an RPM (desktop file, hicolor icons, binary) and the raw binary.
2. **Server: `source_url` becomes nullable, end to end** — migration, upload schema marks it optional, the capture page renders without the "Open original page" link when absent, previews/flat rendering unaffected. Tests cover a source-less capture's page and API responses. PLAN.md §5/§7/§8 updated in the same change, noting the original always-link requirement was browser-capture-specific by construction.
3. **Consistent app identity:** one reverse-DNS app id (derive from the owner's domain) used by the desktop file, DBus/portal calls, and notifications — portal permission persistence keys on it, so inconsistency breaks the remembered-screenshot grant. Say this in a comment where the id is defined.
4. **Capture flows:** three user-facing actions (full screen / region / window) from the tray menu, desktop actions, and global shortcuts — each a genuinely distinct flow on Plasma, using the portal where its implementation delivers the mode well and ScreenShot2 where it doesn't (full-screen and window picking are its strengths; determine region's best path empirically). The ScreenShot2 authorization annotation ships in the desktop file with a comment explaining why it must match the installed file. Record per-mode findings — which API serves which mode on Plasma 6 and why — in the client README.
5. **Upload + open:** the portal-returned PNG posts to the real endpoint with the bearer token, a generated title (mode + timestamp), and no `source_url`; the returned `pageUrl` opens via the portal's OpenURI (system default browser); success and failure surface as portal notifications, with 401 specifically directing to reconfiguration. Client-side size check against `MAX_UPLOAD_MB` mirrors the extension's behavior. TLS via rustls works against the real cert on the nonstandard port.
6. **Config + secrets:** server origin and token via `snapping-turtle --configure` and an XDG-path config file; the token lives in the Secret Service keyring when available, else a 0600 file — and CLAUDE.md rule 3 crosses the language boundary: the token and full capture-page URLs never appear in logs or error output (8-char prefixes only).
7. **File hygiene:** determine where the portal actually lands its file on Fedora 44; clean up transient files that are ours, never touch any copy the user's own screenshot settings saved. A test or documented manual check proves no litter accumulates across ten captures.
8. **Autostart, as a choice:** offered during `--configure` (portal Background/autostart request, or an autostart desktop entry), defaulting on for a tray-resident app but trivially reversible; document how to disable.
9. **Cross-component integration test in CI:** boot the real server from the repo harness, run the client binary's upload path against it with a fixture PNG, assert the capture row exists and its page renders — the same "match the implemented contract" discipline M2 applied, now enforced by a compiler in a different language.
10. **`client-linux/TESTING.md`:** manual checklist — all three modes on Plasma Wayland (the primary target), permission persistence on the second full-screen capture, the tray menu, global shortcuts through Plasma's grants UI, the 401/oversize error paths, and a GNOME session only if one is available (tray via extension, portal-only modes). Run what the environment allows; the rest is marked unverified for the human, never claimed.
11. **Docs:** README gains the Linux client section (install from RPM, configure, capture); the deployment checklist's Phase 4 gains the client; PLAN.md's architecture section adds the client as a peer of the extension.

## Explicitly out of scope — do not start these

Flatpak packaging (note in §17 — likely the better long-term distribution, deliberately second); compositor paths beyond the two sanctioned APIs (grim/slurp/wlroots → §17); GNOME-specific verification and polish (§17 — the portal path merely keeps working); macOS/Windows clients; any in-client annotation UI (the browser page is the editor, by design); X11-specific code (the portal covers X11 sessions as-is); server changes beyond the nullable `source_url` in item 2.
